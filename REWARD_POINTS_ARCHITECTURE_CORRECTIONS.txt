C1. DUPLICATE BILL CONTROL — CONFLICT RESOLVED
================================================================================

The earlier partial unique index on (business_id, bill_reference_key,
business_day) was wrong: a DB unique index cannot be selectively bypassed by an
Admin override, and it ignored location. Replaced with a NULLABLE DEDUPE GUARD
KEY, relying on SQLite treating NULLs as distinct — the same mechanism the
repository already depends on for customer_rewards.issuance_key.

--------------------------------------------------------------------------------
Guard key construction
--------------------------------------------------------------------------------

  dedupe_guard_key = "bill:" + business_id + ":" + location_id + ":"
                            + business_day + ":" + bill_reference_key

  bill_reference_key = billReference.trim().toUpperCase()
                                    .replace(/[\s\-_/.]/g, "")

  business_day       = YYYY-MM-DD in businesses.timezone
                       (fallback DEFAULT_TIMEZONE = Africa/Johannesburg)

Location is part of the identity, so two Fives locations issuing receipt "1042"
on the same day never collide.

--------------------------------------------------------------------------------
The exact index
--------------------------------------------------------------------------------

  CREATE UNIQUE INDEX points_awards_dedupe_guard_unq
    ON points_awards (dedupe_guard_key);

No WHERE clause. This deliberately avoids the repository's known SQLite
partial-index limitation entirely.

--------------------------------------------------------------------------------
Three behaviours from one index
--------------------------------------------------------------------------------

  CASE                | dedupe_guard_key                  | RESULT
  --------------------|-----------------------------------|--------------------
  Normal award        | full guard string                 | Second attempt hits
                      |                                   | unique index -> 409
  Admin/Owner         | NULL                              | Never collides;
  override            |                                   | duplicate_override=1
                      |                                   | reason + actor req'd
  After full reversal | set to NULL, original copied to    | Slot freed; same
                      | released_guard_key                | receipt may be
                      |                                   | legitimately
                      |                                   | re-awarded

Override requires role admin or owner, a duplicate_override_reason of at least
5 characters, and writes audit_logs action
"admin.points_award_duplicate_override" with the attempted guard key, the
colliding award id, and the reason.

released_guard_key preserves the original identity permanently for audit even
though the live key is NULL.

POS readiness is unaffected: a POS adapter supplies its own transaction
reference as billReference with source = "pos", and the identical guard applies.

C2. AWARD IDEMPOTENCY — EXACT MODEL
================================================================================

One award writes TWO ledger rows, so the client key cannot be the ledger key.

  KEY                                   | STORED ON            | UNIQUENESS
  --------------------------------------|----------------------|-------------------
  request_idempotency_key (client-gen)  | points_awards        | UNIQUE (business_id,
                                        |                      | request_idempotency_key)
  points-earn:<awardId>                 | loyalty_transactions | existing global
                                        | .idempotency_key     | unique index
  points-bonus:<awardId>                | loyalty_transactions | existing global
                                        | .idempotency_key     | unique index

Child keys are DERIVED FROM THE SERVER-GENERATED awardId, so they are unique by
construction and need no coordination with the client.

--------------------------------------------------------------------------------
Write sequence
--------------------------------------------------------------------------------

  1  quote = calculate(eligibleSpendCents, rate, promotions)  // pure, no writes
  2  awardId = newId(); earnTxId = newId(); bonusTxId = newId()
  3  db.batch([
       INSERT points_awards { id: awardId, request_idempotency_key,
                              dedupe_guard_key, ...snapshot },

       INSERT loyalty_transactions { id: earnTxId,  type:'earn',  quantity:+base,
                                     idempotency_key:'points-earn:'+awardId,
                                     points_award_id: awardId,
                                     spend_amount_cents: eligibleSpendCents },

       // only when bonus > 0
       INSERT loyalty_transactions { id: bonusTxId, type:'bonus', quantity:+bonus,
                                     idempotency_key:'points-bonus:'+awardId,
                                     points_award_id: awardId,
                                     related_transaction_id: earnTxId }
     ])

db.batch() is a single implicit D1 transaction and rolls back entirely on any
error, so a partial award is impossible.

--------------------------------------------------------------------------------
Deterministic error disambiguation — NO error-string parsing
--------------------------------------------------------------------------------

  on batch error:
    a = SELECT * FROM points_awards
         WHERE business_id=? AND request_idempotency_key=?
    if a  -> idempotent replay: reconstruct and return the ORIGINAL result,
             write nothing

    b = SELECT * FROM points_awards WHERE dedupe_guard_key=?
    if b  -> 409 duplicate bill; surface b.total_points / b.created_at /
             b.staff_id
    else  -> 500 unexpected

A network retry therefore returns the original totals and creates ZERO
additional ledger rows. An optional fast-path lookup by
request_idempotency_key before the batch avoids the exception in the common
retry case.

C3. ATOMIC CUSTOMER POINT REDEMPTION — COMPLETE ALGORITHM
================================================================================

The earlier "issue then compensate" approach is WITHDRAWN. Correctness now comes
from a CONDITIONAL INSERT whose WHERE clause re-evaluates the ledger balance
inside the same statement and the same transaction, so the reward row can only
exist if the deduction legitimately applied.

--------------------------------------------------------------------------------
Preconditions resolved before the batch
--------------------------------------------------------------------------------

  P1  program = points program; 409 if missing or active = 0
  P2  item    = points_catalogue_items (active=1, archived_at IS NULL);
                404 otherwise
  P3  reward  = reward_definitions (active=1); 409 otherwise
  P4  cost    = item.points_cost              // re-read now, snapshotted below
  P5  fast-path: SELECT points_redemptions
                 BY (business_id, customer_id, request_key)
                 -> if found, return the ORIGINAL result immediately
  P6  balance = SUM(quantity); if balance < cost -> 422
                (advisory only; the DB is the authority)
  P7  per-customer limit window check          (best-effort advisory)
  P8  locationId = resolvePointsRedemptionLocationId(businessId)
  P9  txId, rewardId, redemptionId = newId() x3
      expiresAt = reward.validDays ? now + validDays*DAY_MS : null

P8 exists because loyalty_transactions.location_id is NOT NULL and a customer
self-redemption has no till. Resolve the business's single active location,
excluding LEGACY_HIDDEN_LOCATION_NAME, ordered by created_at for determinism; if
none exists, fail with a configuration error. DO NOT attempt to make the column
nullable — SQLite cannot alter it without a table rebuild.

--------------------------------------------------------------------------------
The atomic batch — three conditional statements
--------------------------------------------------------------------------------

-- A. Deduct. The balance is re-evaluated AT WRITE TIME, inside this transaction.
INSERT INTO loyalty_transactions
  (id, business_id, location_id, customer_id, staff_id, program_id,
   transaction_type, quantity, spend_amount_cents, bill_reference, notes, reason,
   approved_by, idempotency_key, points_award_id, related_transaction_id, created_at)
SELECT
  :txId, :businessId, :locationId, :customerId, NULL, :programId,
  'redeem', -:cost, NULL, NULL, :notes, NULL,
  NULL, :ledgerKey, NULL, NULL, :now
WHERE (
  SELECT COALESCE(SUM(quantity), 0)
    FROM loyalty_transactions
   WHERE customer_id = :customerId AND program_id = :programId
) >= :cost;

-- B. Issue the wallet reward ONLY if A applied.
INSERT INTO customer_rewards
  (id, business_id, customer_id, reward_definition_id, status, issued_at,
   expires_at, redeemed_at, redeemed_by, location_id, redemption_transaction_id,
   issuance_key, created_at)
SELECT
  :rewardId, :businessId, :customerId, :rewardDefinitionId, 'available', :now,
  :expiresAt, NULL, NULL, NULL, NULL,
  :issuanceKey, :now
WHERE EXISTS (SELECT 1 FROM loyalty_transactions WHERE id = :txId);

-- C. Record the redemption ONLY if A applied.
INSERT INTO points_redemptions
  (id, business_id, program_id, customer_id, catalogue_item_id, reward_definition_id,
   catalogue_item_name, points_cost, ledger_transaction_id, customer_reward_id,
   request_idempotency_key, created_at)
SELECT
  :redemptionId, :businessId, :programId, :customerId, :catalogueItemId, :rewardDefinitionId,
  :itemName, :cost, :txId, :rewardId, :requestKey, :now
WHERE EXISTS (SELECT 1 FROM loyalty_transactions WHERE id = :txId);

  :ledgerKey   = "points-redeem:" + customerId + ":" + requestKey
  :issuanceKey = "points-redeem:" + txId

CRITICAL CORRECTION: customer_rewards.redemption_transaction_id is set to NULL
at issuance. In the existing engine that column means "the transaction that
CONSUMED this reward" and is written by redeemCustomerReward at the till
(worker/lib/loyalty.ts:574). Writing the points-spend id there would be
overwritten later and would corrupt its meaning. The points-spend -> issued-
reward link lives on points_redemptions.customer_reward_id.

These three statements are issued as a single db.batch([...]). Drizzle's
conditional INSERT ... SELECT ... WHERE is awkward to express fluently — use
db.run(sql`...`) for A, B and C and keep them raw and explicit.

--------------------------------------------------------------------------------
Determining the outcome
--------------------------------------------------------------------------------

The PRESENCE OF THE points_redemptions ROW IS THE SINGLE SUCCESS SIGNAL.

  after batch (no exception):
    r = SELECT points_redemptions
         WHERE business_id=? AND customer_id=? AND request_idempotency_key=?
    if r  -> success: newBalance = SUM(quantity); return { balance, reward }
    else  -> 409 "You do not have enough points for this reward."
             // nothing was written

--------------------------------------------------------------------------------
On exception (retry with the same key)
--------------------------------------------------------------------------------

Statement A violates the unique idempotency_key, the batch rolls back entirely,
then:

  catch:
    r = SELECT points_redemptions
         WHERE (business_id, customer_id, request_idempotency_key)
    if r  -> return the ORIGINAL result (one reward, unchanged balance)
    else  -> rethrow

--------------------------------------------------------------------------------
Two concurrent requests, DIFFERENT keys — the required invariant
--------------------------------------------------------------------------------

Balance 1,000, cost 1,000. D1 serialises writes to a single SQLite instance:

  REQUEST   | A SUBQUERY        | A            | B                  | C    | OUTCOME
  ----------|-------------------|--------------|--------------------|------|---------
  Request 1 | 1000 >= 1000 true | inserts -1000| EXISTS(tx1) true   | row  | SUCCEEDS
            |                   |              | -> reward issued   |written|
  Request 2 | 0 >= 1000 false   | 0 rows       | EXISTS(tx2) false  | 0 rows| 409
            |                   |              | -> 0 rows          |      |

ONE reward exists. Final balance is exactly 0. The losing request never issues a
reward, so NO COMPENSATION PATH IS USED IN THE NORMAL FLOW. Both batches commit
cleanly; the loser simply wrote nothing.

--------------------------------------------------------------------------------
Failure cleanup
--------------------------------------------------------------------------------

There is none to perform. The batch is atomic, so every outcome is either "all
three rows" or "no rows". No pending state machine, no sweeper job, and no
cached-balance drift.

Add one non-compensating post-write assertion for observability only: if
SUM(quantity) < 0 after a successful redemption, log an error — it would
indicate a D1 isolation regression, not a recoverable condition.

C5. PROMOTION AND CATALOGUE DELETION — HISTORICAL INTEGRITY
================================================================================

SNAPSHOTS ARE MANDATORY, NOT OPTIONAL. Ids alone are insufficient because a name
may legitimately be edited. Every historical row carries id AND name AND applied
value:

  TABLE               | SNAPSHOTTED
  --------------------|--------------------------------------------------------
  points_awards       | multiplier_promotion_name, applied_multiplier_bp,
                      | bonus_promotion_name, applied_fixed_bonus_points,
                      | rate_points, rate_spend_cents, base_points, bonus_points
  points_redemptions  | catalogue_item_name, points_cost

History therefore renders correctly with zero joins to live configuration, and
editing a promotion name or a catalogue price can never rewrite a past
transaction.

--------------------------------------------------------------------------------
Lifecycle
--------------------------------------------------------------------------------

Both tables use a three-state lifecycle rather than deletion:

  STATE     | COLUMNS                                | BEHAVIOUR
  ----------|----------------------------------------|-------------------------
  Live      | enabled/active = 1, archived_at = NULL | evaluated / listed
  Disabled  | enabled/active = 0, archived_at = NULL | not evaluated / not
            |                                        | listed; freely re-enabled
  Archived  | archived_at set                        | never evaluated, never
            |                                        | listed, hidden from the
            |                                        | default admin list

--------------------------------------------------------------------------------
Deletion policy
--------------------------------------------------------------------------------

DELETE is permitted ONLY for never-used records, checked before deletion in the
same style as the existing isImageKeyStillInUse guard:

  canDeletePromotion(id)     = NOT EXISTS (SELECT 1 FROM points_awards
                                            WHERE multiplier_promotion_id = id
                                               OR bonus_promotion_id = id)

  canDeleteCatalogueItem(id) = NOT EXISTS (SELECT 1 FROM points_redemptions
                                            WHERE catalogue_item_id = id)

If used -> 409 with "This has been used by real transactions. Archive it
instead." and the archive action offered inline. ON DELETE RESTRICT on every
referencing FK is the database-level backstop should the application check ever
be bypassed.

Archiving a catalogue item does NOT touch already-issued customer_rewards; those
vouchers remain valid until they are redeemed or expire.
